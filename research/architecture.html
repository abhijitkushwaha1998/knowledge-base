Org Knowledge Base Architecture

Option B from the landscape report: permissively licensed libraries composed around one Postgres. No per-document permissions by design: whatever is connected is readable by every caller the gateway admits.

How a record gets in

Connectors list each source and hand records to CocoIndex. It fingerprints every record against the documents table, skips anything unchanged, and otherwise writes chunks, embeddings and graph edges in one transaction. A record that disappears from the source has its chunks, vectors and edges deleted on the next run.

Code takes a separate path. codebase-memory-mcp runs per repository, builds its own SQLite graph including HTTP, gRPC and GraphQL calls between services, and that graph is exported into the shared edges table so a service can be joined to its runbook and its incidents.

How a question gets answered

Every call reaches the gateway with an API key or an SSO login. The gateway issues one SQL statement: vector similarity, BM25 and one graph hop, fused with RRF, and returns ranked chunks with links back to the source. There is no per-document filtering: any caller the gateway admits can read anything that was indexed, so the choice of which spaces, channels and repositories to connect is the access control.

What we build ourselves

  • The gateway: MCP plus REST, caller authentication, a tool allow-list, audit, no destructive tools.
  • Connector gaps: Teams and meeting transcripts forked from Onyx's MIT core; a Draw.io and Lucidchart parser.
  • The export from codebase-memory-mcp's SQLite graph into edges.
  • The organizational schema of the edges table: service, repo, team, person, doc, incident, runbook, table, diagram.
